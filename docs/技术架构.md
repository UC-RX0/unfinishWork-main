## 2. ECS 框架

### 2.1 数据布局

- `ComponentManager`：按组件类型分桶（SoA），`BitSet` 记录实体拥有哪些组件
- `ComponentArray`：同类型组件的紧凑数组
- `EntityPool`：实体 ID 复用（`freeList` + `generation` 计数）

### 2.2 遍历顺序（**关键约束**）

`query()` 的返回顺序 = `entitySignature` 的插入顺序。

快照还原时必须按原顺序重建 `entitySignature`，否则**同一份输入会算出不同结果**，确定性直接崩掉。这是快照里为什么要单独存 `entityOrder` 的原因。

### 2.3 系统调度

`SystemManager` 按优先级排序，同优先级按注册顺序。优先级划分：

| 区间 | 段 | 规则 |
|---|---|---|
| -1 ~ 140 | **逻辑段** | 只读写组件数据，不碰节点 |
| 200 ~ 500 | **渲染段** | 只读组件、写节点，不回写逻辑（唯一例外见 §4.3） |
| 1000+ | **校验段** | 校验和 / 快照自检 / 探针 / 断言 |

## 3. 确定性基座

### 3.1 随机源

`PRNG`（mulberry32），全程只用位运算 + `Math.imul`：

- 状态是单个 32 位整数 → 快照成本近乎为零
- 跨引擎 bit-identical（V8 / JSC 结果一致）
- **纪律**：全局只有一个实例；所有随机消费必须在逻辑帧内且顺序固定；绝不用它做纯表现（粒子、抖动）

### 3.2 数学

`MathUtil` 刻意**不含任何超越函数**（sin / cos / atan2）。原因：IEEE-754 下四则运算与 `sqrt` 是正确舍入的，跨引擎必然一致；而超越函数的实现精度不保证一致，是分叉的常见来源。

周期起伏用**三角波** `tri(x)` 替代 `sin`——形状足够柔和，且是纯算术。

### 3.3 固定步长

`FixedStepClock` 两段式：

```ts
canStep(): boolean        // 时间够不够跑一帧
consumeStep(): void       // 确认要跑了，才扣时间
```

**为什么不能是一段式**：锁步等待期间如果提前扣掉时间，那些时间会被永久吞掉 → 客户端越跑越慢。改成两段式后，等包期间时间留在累加器里，包到了立刻连续补上。

单次渲染帧最多补跑 `maxCatchUp`（默认 8）帧，超出即丢弃积压——防止死亡螺旋。

### 3.4 校验和

`ChecksumSystem` 把所有关键组件字段按**固定顺序**混合成一个 32 位值：

- 顺序固定 → 同一世界状态必得同一校验和
- 服务端跨客户端比对，检测分叉

## 4. 逻辑 / 渲染分层

### 4.1 为什么要拆

原来 `AnimPlaySystem` 一个系统同时做"推进帧索引"和"给 Sprite 换图"，导致逻辑帧和渲染帧被绑死——逻辑帧率降不下去、无法插值、无法回滚。

拆成：

| 系统 | 优先级 | 职责 |
|---|---|---|
| `AnimTickSystem` | 140（逻辑） | 推进 `frameIndex` / `timer` / `currentTrigger` / `isComplete` |
| `AnimRenderSystem` | 500（渲染） | 把 `frameIndex` 映射到 `Sprite.spriteFrame` |

同样地 `WeaponSyncSystem` 拆成 `WeaponAimSystem`(10, 逻辑) + `WeaponViewSystem`(209, 渲染)。

**验证**：拆分后校验和保持 `c4295458` 不变 → 证明是行为等价重构。

### 4.2 怪物表现：纯函数

```ts
evalMonsterVisual(state, 帧龄, seed, 朝向) → { offsetX, offsetY, scale, angle, tint }
```

纯函数意味着：可重放、可回滚、不因漏清状态而"卡住"、不会在回滚后残留上一次的表现。

### 4.3 唯一的反向写入

`AnimRenderSystem` 在 clip 动画播放结束时会回写 `anim.isComplete = true`。

这是**刻意保留**的：clip 的时间轴归引擎管，逻辑层无法独立推算播放是否结束。

> 推论：clip 动画不适合做"影响玩法时序"的表现。攻击这类需要精确对齐伤害帧的动画必须用序列帧。

## 5. 帧同步（Lockstep）

### 5.1 原则

> **服务端不跑任何游戏逻辑。**

服务端只做三件事：推进帧号、给输入盖章、广播。一旦服务端参与模拟，就退化成状态同步。

### 5.2 协议

| 消息 | 方向 | 内容 |
|---|---|---|
| `welcome` | S→C | 玩家索引、种子、人数、当前帧号 |
| `start` | S→C | 房间成型广播：人数、种子、起始帧 |
| `frame` | S→C | 帧号 + 所有玩家的输入（整数定点） |
| `input` | C→S | 本地当前输入（持续上报） |
| `checksum` | C→S | 校验和上报（每 60 帧一次） |
| `desync` | S→C | 分叉告警 |
| `roster` | S→C | 房间人数变化 |

输入是**整数定点**（方向 ×1000、力度 ×1000），保证各端字节完全一致。

### 5.3 房间先成型，再开局

**这是端到端测试抓出来的真实 bug。**

原实现：先到的客户端只建 1 个玩家实体，后到的建 2 个 → 两端实体集合不同 → 校验和必然不等。服务端从 `frame=420` 开始报分叉。

修法（帧同步的标准要求）：
- 服务端人数凑齐才发帧，并广播 `start`
- 客户端收到 `start` 之后才建世界，按 `start.playerCount` 建对应数量的玩家

### 5.4 帧号对齐

客户端必须用 `welcome.frame` / `start.frame` 初始化自己的帧号。

否则客户端从 0 数帧、而输入缓冲按服务端帧号索引 → `ready()` 永远 false → **世界直接卡死**。这是第一次联机时"一只怪都刷不出来"的原因。

### 5.5 降级策略

`connect()` 抛错 → catch → 回退单机继续跑。

**联机失败不应该让整个游戏起不来。** 这条也是从真实问题里修出来的。

## 6. 客户端预测与回滚

### 6.1 延迟的来源

纯锁步下，本地操作要等"客户端→服务端→客户端"一个来回才生效，约 48ms（局域网）/ 100~200ms（公网）。表现为"操作晚 1~2 帧才生效"。

### 6.2 本实现的核心决策

**本地输入预测，远端输入不猜。**

| 玩家 | 输入来源 | 延迟 |
|---|---|---|
| 本地 | 采样即生效（预测） | **0** |
| 远端 | 等服务端权威帧 | 一个来回（无所谓，反正是别人的操作） |

**为什么不猜远端输入？** 这是本实现最重要的一条决策，代价是踩了一整轮坑：

1. 猜远端输入会导致回滚极其频繁 —— 远端输入几乎每帧都变，
   实测 900 帧触发 **573 次**回滚，每次还要重演十几帧，CPU 浪费巨大。
2. 更糟的是"重演时重新预测"会让**同一帧在不同时间算出不同状态**，
   状态漂移，永远收敛不了。

改成远端输入等权威帧后，回滚次数降到合理水平（远端输入真正变化时才回滚），
而**本地操作依然是零延迟** —— 因为本地输入从来不需要等服务端。

### 6.3 已结算帧（settled frame）

这是预测回滚里最容易被忽略的概念。

客户端跑到服务端前面之后，当前帧的状态里可能混着"还没被服务端确认的预测输入"。
这时的校验和拿去和别的客户端比对，**必然不一致** —— 但那不是分叉，只是两端还没走到同一步。

所以比对必须用**已结算帧**：

> 一帧"已结算" = 该帧所有输入都被服务端确认，且本端已按权威输入重演过。

`RollbackController.settledFrame` 追踪这个水位线，`getReportableChecksum()` 只返回已结算帧的校验和。

### 6.4 预测回滚的三个要素

| 要素 | 实现 |
|---|---|
| **状态快照** | `World.captureSnapshot()` / `restoreSnapshot()`，含组件、实体顺序、系统私有状态、实体池、随机数、帧号 |
| **预测输入** | 本地输入在采样的那一帧立即写入 `FrameInputBuffer`，不等服务端回包 |
| **回滚重演** | 收到权威帧后比对本地实际使用的输入，不一致则还原到分歧点并用权威输入重演 |

### 6.5 快照的实现要点

1. **实体顺序**必须原样还原（见 §2.2）
2. **系统私有状态**也要快照 —— `EnemySpawnSystem.nextSpawnFrame`、`WaveSystem.spawnTimer` 不属于任何组件，不存的话回滚后它们停在上一个时间点，重演结果必然不同。为此给 `ISystem` 加了 `captureState` / `restoreState` 钩子。
3. **深拷贝规则**：原始值/纯对象/数组/Map/Set 递归拷贝；引擎对象（Node / SpriteFrame / AnimationClip / Vec3）**保持引用不拷贝**
4. **视图层对齐**：还原后对比前后实体节点集合，把窗口内新建实体的节点销毁，否则场景里留下"幽灵怪物"
5. **基线快照必须在建实体之后采集**：回滚到第 1 帧时需要"第 0 帧之后"的状态作为还原点。早采会导致回滚找不到快照 → 第一次分歧就回滚失败 → **永久分叉**。
6. **重演后必须重新采集快照**：否则下一次回滚会把错误状态带回来，误差会累积。

### 6.6 输入归属：帧号

客户端上报输入时带上帧号，服务端按帧号盖章回传：

```
客户端采样第 N 帧的输入 → 报"N 帧的输入" → 服务端在第 N 帧盖章回传
```

好处：**本地玩家的权威值 = 客户端自己采样的值，逐位相同** —— 本地输入永远不会触发回滚。

服务端必须**等该帧的输入到齐才能广播**。否则会用"最近一次上报"盖上还没到的帧的章，产生无谓的回滚。

### 6.7 回滚重演必须沿用"当时用的预测值"

重演时如果重新预测，会得到不同结果 → **回滚不幂等** → 状态漂移。

所以：权威输入优先，没有权威就用 `usedInputs` 里存的"当时用的预测值"。

### 6.8 节点延迟销毁

回滚要求"实体在回滚后能复活"，所以死亡时不能直接 `destroy()` 节点。

- 逻辑层：血量归零立即移除实体
- 视图层：节点先隐藏，等过了**回滚窗口**（`DeferredNodeRecycler.rollbackWindowFrames`，默认 300 帧）才真正回收
- 回滚时：`World.restoreSnapshot` 复活隐藏的节点，并撤销待回收标记

### 6.9 中途加入

新玩家在开局后加入时：
1. 服务端发 `start`（含当前帧号 + 完整历史输入包）
2. 客户端从第 0 帧开始**追帧重演**到当前帧
3. 追帧期间不渲染，只跑逻辑
4. 追完后进入正常锁步

追帧期间用独立的步数上限，防止一次追太多帧卡死。

## 7. 资源层（ResBridge）

### 7.1 为什么需要这一层

ECS 是严格同步架构——`System.update()` 必须在一帧内跑完并返回，无法容纳 `await`。而 Cocos 的资源加载天生异步。

直接带 async 进 ECS 的后果：
1. System 内部逻辑被切割成多帧，实体状态出现"半初始化"中间态
2. 谁都可能触发隐式加载，卡顿位置不可预测
3. 缺资源时是运行期空引用崩溃，而不是启动期可发现的问题

### 7.2 单向状态机

```
Idle ──boot()──► Loading ──全部加载完──► Sealed
 ▲                                            │
 └────────── 失败，missingList 非空 ──────────┘
```

- **启动期**：`boot()` 一次性预加载清单里的全部资源 —— 全项目**唯一允许 await 的地方**（`GameLaunch.onLoad`）
- **运行期**：`get` / `spawn` 全是纯内存读取，零 await，缺失立即抛错
- **封盘**：`resMgr.seal()` 关闭底层加载能力，之后任何绕过本层偷调 `resMgr.loadXxx` 的代码会直接抛异常

### 7.3 节点池

启动期按 `prewarm` 预热实例（子弹预热 32 个覆盖约 3~5 秒连续射击）。运行期 `spawn()` 优先复用，池空才 `instantiate`。

## 8. 验证体系

### 8.1 headless 环境（`tools/headless/`）

在 Node 里跑真实 ECS 逻辑，不依赖编辑器。

```
tools/headless/
├── cc-stub.d.ts + stub/*       引擎 / 资源层 / UI 层桩
├── run.js                      单机：确定性 + 四态覆盖 + 不变量
├── game-flow-test.js           完整游戏流程（通关 / 失败 / 确定性 / 波次表）
├── rollback-test.js            回滚往返自检
├── rollback-verify.js          回滚【绝对正确性】（对比纯权威基准）
├── net-client.js / net-test.js 帧同步端到端
├── test-all.js                 统一入口
└── README.md
```

**关键**：`SceneBuilder.ts` 把建实体逻辑从 `GameLaunch` 抽出，编辑器与 headless 共用同一套代码路径。否则 headless 的结论对编辑器不成立，等于白测。

### 8.2 五个层次的自检

| 层次 | 工具 | 抓什么 |
|---|---|---|
| **确定性** | 两次运行比对校验和 | 逻辑顺序错乱、随机序列乱序、输入状态残留 |
| **不变量** | `GameTestRunner` | 位置越界、血量异常/为负、方向未归一化、实体数泄漏 |
| **流程** | `game-flow-test.js` | 通不了关、失败不判定、波次不推进、数值失衡 |
| **回滚正确性** | `rollback-verify.js` | 重演用了错的输入、快照漏状态、实体顺序变了 |
| **端到端** | `net-test.js` | 分叉、帧号错位、房间成型 |

### 8.3 「两端一致」不等于「正确」

这是本项目最重要的一条验证原则。

两个客户端**可能因为同样的 bug 一起错**，校验和照样一致。所以：

- `net-test.js` 验证的是"两端一致"（排除分叉）
- `rollback-verify.js` 验证的是"与纯权威基准一致"（排除共同的错误）

两者都通过，才敢说回滚是对的。

### 8.4 调试手段本身可能不可靠

> 教训：曾在 Cocos 编辑器预览环境里，给已存在的节点改 `name` 写不进去（写进去读回来还是原名），导致校验探针长时间"不触发"，看起来像 `ChecksumSystem` 没被调用。

真相是：服务端一直收到校验和 → `update` 一直在跑；把节点**创建名**改成 `DET_PROBE_V2` → 立刻出现 → 说明新代码在跑；但同一函数里的 `probe.name = ...` 就是不生效。

修法：取消改名，改成"触发时创建节点，名字里直接带上 `local/frame/sum/count`"。

**结论**：生产路径（如校验和上报）要用服务端日志验证，不要依赖节点改名这种花活。

## 10. 已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| 中途加入需追帧重演 | 服务端需持续广播历史输入包（带宽浪费） | 加入延迟约 1~2 秒 |
| clip 动画完成状态靠轮询 | 引擎持有时间轴，逻辑层无法独立推算 | 死亡判定用帧龄而非 clip 回调 |
| 回滚有窗口上限 | 快照窗口 300 帧，超出范围的分歧无法回滚 | 极端网络抖动时可能放弃回滚（会打警告） |
| 无音频 | 工程内无音频资源 | — |
| HUD 用代码构建 | 没有 UI 图集，血条/文字用 Graphics 绘制 | 样式朴素但零依赖 |
| 编辑器预览未自动化 | Cocos MCP 插件会周期性崩溃 | 验证依赖 headless（已覆盖全部逻辑） |

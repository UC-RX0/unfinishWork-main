## 3. headless 测试

headless 在 Node 里跑真实 ECS 逻辑，**不依赖编辑器**。编辑器插件会周期性崩溃，验证不能只靠它。

### 3.0 一条命令跑完全部验证

```bash
node tools/headless/test-all.js          # 不含联机测试（快）
node tools/headless/test-all.js --net    # 含联机端到端测试
```

输出汇总：

```
✅ 单机确定性 + 四态覆盖 + 不变量
✅ 完整游戏流程（通关 / 失败 / 确定性 / 波次表）
✅ 回滚往返自检
✅ 回滚绝对正确性（对比纯权威基准）
✅ 帧同步端到端（两客户端 + 服务端）
==================================================
🎉 全部验证通过
```

### 3.1 编译

```bash
cd G:/unfinishWork-main
node "E:/CocosEngine/Creator/3.8.7/resources/app.asar.unpacked/node_modules/typescript/bin/tsc" -p tools/headless/tsconfig.json
```

> headless 的桩比真实 cc 精度低，类型报错是预期的，只需要产出 JS。

### 3.2 工程类型检查

```bash
node "E:/CocosEngine/Creator/3.8.7/resources/app.asar.unpacked/node_modules/typescript/bin/tsc" -p temp/tsconfig.check.json --noEmit
```

这条是**必须过的**（0 错误）。

### 3.3 单机测试

```bash
node tools/headless/run.js 3000 combat
```

输出：

```json
{
  "mode": "combat",
  "frames": 3000,
  "checksum": "8d662d06",
  "states": "Idle=18,Move=39,Attack=5,Hit=26,Dead=17",
  "assertions": 0
}
```

| 参数 | 含义 |
|---|---|
| 第 1 个 | 跑多少逻辑帧（默认 3000） |
| 第 2 个 | `combat`（脚本输入+射击）/ `idle`（无输入） |

**两次运行 checksum 必须一致** —— 这是确定性验证。

### 3.4 完整游戏流程测试

```bash
node tools/headless/game-flow-test.js
```

验证整局能不能跑完：

- **通关路径**：从准备一路打到第 10 波胜利，输出击杀数 / 得分 / 用时
- **失败路径**：玩家阵亡 → 失败结算
- **确定性**：两次运行校验和一致
- **波次表自洽**：怪物数递增、血量倍率不下降

调数值后**必须跑这个** —— 它会输出血量轨迹，用数据判断平衡，而不是靠感觉。

### 3.5 回滚验证（两个层次）

```bash
node tools/headless/rollback-test.js      # 往返自检
node tools/headless/rollback-verify.js    # 绝对正确性
```

`rollback-verify.js` 是更严格的那个：**不只验证两端一致**（两个客户端可能一起错），
而是与"纯权威输入从头跑一遍"逐位比对。这才是绝对正确。

### 3.6 端到端帧同步测试

```bash
# 终端 1：起服务端
cd server && npm start

# 终端 2：跑双客户端
node tools/headless/net-test.js 900 600
```

期望输出：

```
客户端A: {"playerIndex":0,"frames":900,"settled":892,"settledSum":"5911d6fc",...}
客户端B: {"playerIndex":1,"frames":900,"settled":892,"settledSum":"5911d6fc",...}
✅ 已结算帧校验和一致：frame=892 sum=5911d6fc
✅ 服务端未报告分叉
```

**注意比对的是已结算帧**（settled 字段），不是当前帧 —— 原因见技术文档。

## 4. 联机联调

### 4.1 启动服务端

```bash
cd G:/unfinishWork-main/server && npm start
```

### 4.2 打开联机开关

编辑 `assets/Script/game/Config/BattleConfig.ts`：

```ts
net: {
    enabled: true,      // ← 改成 true
    url: "ws://127.0.0.1:7788",
    maxPlayers: 2,
},
```

### 4.3 开两个客户端

编辑器预览只能开一个实例。双端一致性需要：

```
构建 → Web 预览 → 用两个浏览器标签页打开同一个地址
```

两端都进入后，服务端自动比对校验和，一旦分叉会打印 `!! 分叉 frame=N`。

### 4.4 收尾

**记得把 `enabled` 改回 `false`**——单机模式是确定性基线的依赖。

> 连不上服务端会自动降级回单机，不会卡住游戏启动。

## 5. 代码规范

### 5.1 逻辑层红线

```ts
// ❌ 绝对禁止
import { Vec3, Node, Color } from "cc";

// ✅ 允许
import { BATTLE_CONFIG } from "../Config/BattleConfig";
```

逻辑层一旦依赖引擎，就没法在 Node 里跑双跑校验和——整套确定性验证立刻失效。

### 5.2 三条纪律

| 纪律 | 原因 |
|---|---|
| 随机只能来自 `logicRng` | `Math.random()` 不可复现，是帧同步最致命的破坏点 |
| 时长一律用逻辑帧 | 浮点秒数累加会漂移，帧号调度是纯整数 |
| 组件字段的"唯一写入者" | 多个系统抢写同一字段（如旧的 `anim.nextState`）必然出 bug |

### 5.3 状态机写法

新状态必须加到 `MonsterStateSystem` 里，并且：

1. 在 `MonsterStateComponent` 上加字段
2. 在 `evalMonsterVisual` 里加表现分支（纯函数）
3. 在 `MonsterStateStats` 里加计数（用于自动验证覆盖）

**不要**在别的系统里写 `anim.nextState` —— 那是旧代码的毛病。

### 5.4 新增系统

1. 继承 `ISystem`，实现 `init()` / `update(dt)`
2. 选好优先级区间（逻辑 / 渲染 / 校验）
3. 在 `System/index.ts` 导出
4. 在 `World.addBase()` 里注册
5. 如果有私有状态，实现 `captureState` / `restoreState`

## 7. 常见陷阱

### 7.1 query() 遍历顺序

`query()` 返回顺序 = `entitySignature` 插入顺序。快照还原必须原样重建，否则同一份输入算出不同结果。

### 7.2 系统私有状态

不属于任何组件的状态（刷怪计时器等）必须快照。给 `ISystem` 加 `captureState` / `restoreState` 就是为此。

### 7.3 边界值互相约束

子弹回收边界必须**小于**不变量断言的余量，否则子弹会落在"没被回收、却已越界"的区间里（第一次修完仍剩 2 次误报就是这个原因）。

### 7.4 帧号对齐

联机时客户端帧号必须用服务端下发的值初始化，否则输入缓冲永远匹配不上，世界卡死。

### 7.5 锁步等待不吞时间

用 `canStep()` / `consumeStep()` 两段式，不要用一次性 `advance()`。

### 7.6 调试手段本身可能不可靠

Cocos 编辑器预览环境里，**给已存在的节点改 `name` 是不可靠的**（写进去读回来还是原名）。

生产路径的验证要用服务端日志 / 校验和上报，不要依赖节点改名。

### 7.7 headless 与编辑器必须同路径

建实体逻辑放在 `SceneBuilder.ts`，两边共用。否则 headless 测出来的结论对编辑器不成立。

### 7.8 资源必须先进清单

任何新资源都要先在 `AssetManifest.ts` 声明，否则 ResBridge 在运行期直接抛错。

## 8. 关键路径速查

| 想做的事 | 改哪里 |
|---|---|
| 调数值 | `game/Config/BattleConfig.ts` |

| 改网络协议 | `game/Net/Protocol.ts` + `server/index.js`（两边必须同步） |
| 加 HUD | `UI/AnimHud.ts` |
